> 适用于 UniMarket 统一商城前台的代码评审流程、评审维度与记录模板。
> 目标：在合并前拦截缺陷、统一风格、沉淀知识，而非事后补救。

## 1. 总体原则

| 原则 | 说明 |
|------|------|
| 合并前置 | 未经评审不得合并到 master（单人项目按自评审清单执行） |
| 小步评审 | 单次评审变更 ≤ 500 行，超长拆分为多个提交/PR |
| 对事不对人 | 评审针对代码，语气中立，给出理由而非命令 |
| 早发现早修复 | 缺陷越早发现修复成本越低 |
| 知识沉淀 | 高频问题沉淀到规范文档，避免重复评审 |

**评审对象**：一切进入主分支的代码（功能/修复/重构/测试），文档变更可不评审。

---

## 2. 评审时机与范围

| 场景 | 评审方式 |
|------|----------|
| 功能分支完成 | 合并前全量评审（PR/MR） |
| 修复分支 | 重点评审修复点及影响面 |
| 重构 | 必须评审（行为不变性验证 + 测试覆盖） |
| 紧急修复 | 先修复上线，24h 内补评审 |
| 单人项目 | 自评审清单 + 次日冷读（隔天看自己的 diff） |

**评审范围**：
- 变更的 diff（必须）
- 变更调用链的上下游（影响面）
- 相关测试是否覆盖关键分支

## 3. 评审流程

```
1. 作者：完成开发 + 自测 + 提交说明（改动了什么/为什么/影响面）
2. 提交：创建 PR/MR（描述含：背景、变更点、测试方式、影响范围）
3. 评审：按 §4 维度逐项检查，产出评论/结论（通过/需修改/驳回）
4. 修改：作者处理评审意见（修复/回应"不采纳及理由"）
5. 复核：评审人确认意见闭环 → 合并
6. 记录：评审结论归档（§7 模板或 PR 记录）
```

**时间要求**：评审意见 1 个工作日内响应；阻塞性缺陷必须修复后再合并。

## 4. 评审维度与检查重点

### 4.1 正确性（最高优先级）

- [ ] 业务逻辑是否符合需求/设计（对照 FR/SDS）
- [ ] 边界条件：空值、超限、并发、重复调用（幂等）
- [ ] 状态机流转是否合法，有无非法跳转
- [ ] 金额计算顺序与精度（BigDecimal、舍入）
- [ ] 事务边界：是否包含外部调用/长循环；回滚是否符合预期
- [ ] 定时任务是否可重跑（幂等）
- [ ] 异步链路：消息补偿、死信、失败处理是否闭环

### 4.2 安全（阻塞级）

- [ ] SQL 注入（`${}`）、命令注入、动态拼接
- [ ] 越权：资源访问是否绑定当前用户/角色
- [ ] 敏感信息：密钥/Token/手机号是否入日志、入库、入响应
- [ ] 支付/第三方回调是否验签
- [ ] 文件上传/下载安全

> 安全项发现即阻塞，未修复不得合并（见《安全编码规范》）。

### 4.3 性能与并发

- [ ] 是否 N+1 查询、循环内查库/发 MQ
- [ ] 是否大事务/长事务
- [ ] 是否合理使用缓存与索引（对照《数据库设计规范》）
- [ ] 锁粒度与死锁风险（多资源加锁顺序）
- [ ] 线程池/并发容器使用是否安全

### 4.4 可维护性

- [ ] 命名符合规范、方法职责单一、无超长方法/超深嵌套
- [ ] 无重复代码（抽取公共方法/工具类）
- [ ] 魔法值是否常量/枚举化
- [ ] 注释是否必要且准确（对照《代码注释规范》）
- [ ] 是否符合分层职责（Controller/Service/Domain）

### 4.5 测试覆盖

- [ ] 核心分支有单测（对照《测试规范》§3 必测清单）
- [ ] 边界与异常路径有覆盖
- [ ] 测试命名规范、断言有效（非空断言）

## 5. 评审记录与缺陷分级

### 5.1 缺陷分级

| 级别 | 定义 | 处理 |
|------|------|------|
| P0 阻塞 | 安全漏洞/数据错误/核心功能不可用 | 必须修复后合并 |
| P1 重要 | 边界缺陷/明显性能问题/规范严重违背 | 建议修复后合并（可带修复计划） |
| P2 建议 | 命名/风格/可读性优化 | 可采纳可记录，不阻塞 |

### 5.2 评审结论

| 结论 | 含义 |
|------|------|
| 通过 | 无 P0/P1 未处理项 |
| 需修改 | 存在 P0/P1，修改后复核 |
| 驳回 | 方案方向错误或安全缺陷，重做 |

## 6. 单人项目自评审清单

> 单人开发没有评审人时，合并前按此清单"扮演评审人"自查：

1. **冷读 diff**：写完搁置一会儿再读自己的 diff，发现直觉问题。
2. **边界枚举**：列出入参边界（空/0/超限/重复/并发）逐一核对。
3. **安全自检**：跑一遍《安全编码规范》§10 检查清单。
4. **数据自检**：下单/退款等关键链路按"成功/失败/重复/超时"四象限验证。
5. **测试补充**：为刚写的逻辑补 2-3 个边界单测。
6. **提交说明**：写清楚"改了什么/为什么/影响面"，便于日后追溯。

## 7. 评审模板

```markdown
## Code Review 记录

- PR/提交：<分支> → master（commit <hash>）
- 评审人 / 日期：<name> / YYYY-MM-DD
- 评审范围：<模块/文件清单>

### 评审意见

| # | 级别(P0/P1/P2) | 文件/位置 | 问题 | 建议 | 状态 |
|---|----------------|-----------|------|------|------|
| 1 | P1 | OrderService.java:88 | <问题> | <建议> | ☐ 待处理 |

### 评审结论
- [ ] 通过
- [ ] 需修改（复核后合并）
- [ ] 驳回

### 知识沉淀
- <本次发现的共性问题 → 是否更新到某规范文档>
```
