## 1. 分支模型总览

采用 **Git Flow 简化版**（适合单人/小团队，去重 release 分支）：

```
master（主分支，长期存在）
  │
  ├── develop（开发集成分支，长期存在，可选）
  │     │
  │     ├── feat/xxx（功能分支，短期）
  │     ├── fix/xxx  （修复分支，短期）
  │     ├── docs/xxx （文档分支，短期）
  │     └── test/xxx （测试分支，短期）
  │
  └── tag v1.0.0（发布标签）
```

| 分支 | 生命周期 | 说明 |
|------|----------|------|
| `master` | 长期 | 稳定可发布代码，禁止直接提交，只接受合并 |
| `develop` | 长期（可选） | 开发集成分支；单人项目可省略，直接在 master 上开短期分支 |
| `feat/*` | 短期 | 功能开发分支，从 master/develop 拉出 |
| `fix/*` | 短期 | 缺陷修复分支 |
| `docs/*` | 短期 | 文档变更分支 |
| `test/*` | 短期 | 测试编写/修复分支 |
| `refactor/*` | 短期 | 重构分支（行为不变） |

> **单人项目建议**：master 即主线，每个功能/文档任务开一个短期分支（如 `feat/order-module`），完成后合并回 master 并删除。

## 2. 分支命名规范

### 2.1 通用格式

```
<type>/<描述>
```

- 类型：`feat` / `fix` / `docs` / `test` / `refactor` / `style` / `perf` / `chore`
- 描述：小写连字符，用业务含义而非日期/人名

### 2.2 示例

| 场景 | 分支名 |
|------|--------|
| 开发订单模块 | `feat/order-module` |
| 修复支付回调 bug | `fix/pay-callback-verify` |
| 编写接口规范文档 | `docs/api-spec` |
| 重构抽奖算法 | `refactor/raffle-algorithm` |
| 补充购物车测试 | `test/cart-service` |

### 2.3 关联需求（可选）

有需求/任务编号时追加编号：

```
feat/order-module/UM-123
fix/UM-456/pay-timeout
```

## 3. 分支生命周期

### 3.1 创建分支

```bash
# 先同步主分支
git checkout master
git pull origin master

# 拉功能分支
git checkout -b feat/order-module
```

### 3.2 开发提交

在功能分支上小步提交（见第 4 节提交流程规范），本地完成后推送到远端：

```bash
git push -u origin feat/order-module
```

### 3.3 合并回主分支

```bash
git checkout master
git pull origin master          # 同步最新
git merge --no-ff feat/order-module   # --no-ff 保留合并记录
git branch -d feat/order-module       # 合并后删除本地分支
git push origin master
git push origin --delete feat/order-module  # 删除远端分支
```

> 单人项目本地合并即可；多人协作走 Pull Request / Merge Request 评审后合并。

### 3.4 发布打标签

每完成一个可发布里程碑（如 Phase 1 完成、M1 达成）打标签：

```bash
git tag -a v0.1.0 -m "Phase 1 基础骨架完成：登录→下单→支付"
git push origin v0.1.0
```

版本号遵循语义化版本：`主版本.次版本.修订`（如 v0.1.0）。

## 4. 提交流程规范

### 4.1 提交信息格式（Conventional Commits）

```
<type>(<scope>): <subject>

[可选 body：说明做了什么、为什么]
```

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档变更 |
| `style` | 格式/注释（无逻辑变更） |
| `refactor` | 重构（不改变功能） |
| `test` | 测试相关 |
| `perf` | 性能优化 |
| `build` | 构建/依赖变更 |
| `ci` | CI 配置变更 |
| `chore` | 杂项（配置、工具） |

### 4.2 提交信息示例

```bash
# 正确
git commit -m "feat(order): 实现订单创建与状态机流转"
git commit -m "fix(pay): 修复支付回调重复处理导致的订单状态错乱"
git commit -m "docs(readme): 补充项目启动说明"

# 多行提交
git commit -m "feat(cart): 实现购物车 Redis 存储

- cart:userId Hash 结构 add/update/remove
- 登录后设备购物车合并
- 实时校验库存与价格"
```

### 4.3 提交粒度原则

- **一个提交只做一件事**：功能、修复、文档分开提交。
- 提交信息首行 ≤ 50 字符，用祈使句。
- 禁止把无关文件混入同一提交（如功能提交夹带格式化改动）。
- 提交前用 `git status` / `git diff --stat` 检查范围。

### 4.4 提交前检查

- [ ] 代码通过编译（`mvn compile`）
- [ ] 相关测试通过（`mvn test`）
- [ ] 无调试代码、无 `System.out` 残留
- [ ] 无密钥/密码/Token 提交（见《开发规范-注释规范》安全约定）
- [ ] 无 `target/`、`node_modules/` 等构建产物

## 5. 合并与发布流程

### 5.1 合并前

```bash
# 确保功能分支基于最新 master
git checkout master && git pull
git checkout feat/xxx && git rebase master   # 或 merge master
```

### 5.2 冲突处理

- 优先使用 `git rebase` 保持历史线性（单人项目）。
- 冲突解决后：`git add <file>` → `git rebase --continue`。
- 解决冲突时遵循"业务正确优先，保留双方合理改动"。

### 5.3 发布流程

```
功能分支开发完成
  → 合并到 master
  → 全量回归（冒烟 + 关键链路）
  → 打 tag 发布
  → 若线上发现缺陷：从 master 拉 fix/xxx 修复 → 合并 → 打 patch tag
```

## 6. 禁止事项

| 禁止 | 原因 | 正确做法 |
|------|------|----------|
| 直接在 master 上提交 | 破坏主分支稳定性 | 开短期分支，合并回 master |
| `git push --force` 到共享分支 | 覆盖他人历史 | 仅在私有分支且确认无误时使用 |
| `git reset --hard` 丢弃未提交工作 | 不可恢复 | 先 `git stash` 或提交备份 |
| 提交构建产物/IDE 配置 | 污染仓库 | 配置 `.gitignore` 排除 |
| 提交密钥/密码/Token | 严重安全风险 | 使用环境变量/配置中心 |
| 一个提交混入多个无关功能 | 难以回滚与评审 | 按功能拆分提交 |
| 合并后立即删除共享分支的历史 | 丢失追溯 | 保留 tag 或合并不带 `--squash` 的关键历史 |
