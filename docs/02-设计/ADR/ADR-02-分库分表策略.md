# ADR-02：保留分库分表（2 库 × 4 表 = 8 分片）

- **状态**：已接受（Accepted）
- **日期**：2026-08-10
- **关联文档**：《设计文档-SDS》§7/§10.4、《开发规范-数据库设计》§8
- **影响范围**：用户/订单/支付/抽奖/拼团等用户维度数据表

## 背景

拼团和抽奖的用户参与记录量级可达亿级，单表无法承载；用户维度数据（订单、积分、券、消息）需要水平扩展能力。

## 决策

采用 **2 库 × 4 表 = 8 分片**，按 `userId` 哈希路由（扰动函数 `hash ^ (hash >>> 16)`，`dbIdx = hash % 2`，`tbIdx = (hash / 2) % 4`），通过 MyBatis 拦截器统一路由。

- 公共配置数据（商品/活动/券模板/拼团队伍/通知任务）放公共库 db00，不分片。
- 分片参数（dbCount/tbCount）参数化，为扩容留接口。

## 后果

- 正面：用户维度数据可水平扩展；分片后单表数据量可控；为亿级参与记录留容量。
- 负面：跨分片 JOIN/事务不可用（需应用层合并/汇总表）；分布式 ID（雪花）依赖。

## 备选方案

- 单库单表：实现简单，但亿级数据无法承载，违背目标量级。
- 中间件分库分表（ShardingSphere）：功能强但引入复杂度；本系统规模下自研拦截器路由足够。

## 演进

数据量增长后可平滑扩容至 **4 库 × 8 表 = 32 分片**（路由参数调整 + 数据迁移脚本）。
