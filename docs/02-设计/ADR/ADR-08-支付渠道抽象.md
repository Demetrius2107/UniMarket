# ADR-08：支付渠道抽象与统一收银台

- **状态**：已接受（Accepted）
- **日期**：2026-08-10
- **关联文档**：《设计文档-SDS》§3.2/§6.10、《接口开发规范》
- **影响范围**：支付领域

## 背景

系统需支持支付宝与微信双渠道支付，未来可能扩展新渠道（银联、云闪付等）。若渠道逻辑硬编码在业务中，新增渠道将改动核心链路。

## 决策

采用**渠道抽象 + 统一收银台**：

- 定义支付渠道接口（`createPayOrder` / `verifyNotify` / `queryPayStatus` / `refund`），支付宝/微信各自实现。
- 统一收银台 `/order/cashier` 根据用户选择路由到对应渠道实现。
- 新增渠道只需实现渠道接口并注册，不修改核心流程。

## 后果

- 正面：渠道扩展成本低；回调验签/幂等逻辑按渠道隔离；统一收银体验一致。
- 负面：渠道差异需在实现层适配（如微信 JSAPI 与支付宝表单），抽象层需保持接口稳定。

## 备选方案

- 渠道硬编码：开发快但扩展性差，违背 NFR-EXT-03。
- 支付网关中间件：功能全但引入外部依赖与成本，当前规模不需要。

## 演进

渠道增多后可引入统一支付网关（聚合支付）替代自研抽象。
