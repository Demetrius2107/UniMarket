## 1. 引言

### 1.1 编写目的

本文档规定统一商城平台（UniMarket）的功能需求与非功能需求，作为系统设计、开发实现、测试验收的依据。阅读对象：产品、研发、测试、运营。

### 1.2 项目背景

UniMarket 是一个面向 C 端用户的、融合多种营销玩法的完整电商平台。它不仅是"一个商城"，更是一个**可运营的营销引擎**——运营人员通过配置化的方式创造抽奖、拼团、积分兑换、签到返利等多种营销活动，驱动用户增长和转化。

系统融合四个既有原项目的能力：支付原型（s-pay）、抽奖（Lottery）、营销（big-market）、拼团（group-buy-market），在其基础上补齐商品、购物车、优惠券、售后、物流、首页运营、消息中心等电商基础能力，形成完整闭环。

### 1.3 需求范围

- **包含**：用户登录、商品浏览与搜索、购物车、下单支付、拼团、抽奖、积分、优惠券、售后、物流、首页运营、消息通知、运营后台（ERP）、风控与监控。
- **不包含**：商家开店/多商户体系、平台间结算清分、原生 App（仅 H5/SPA）、跨境与海外支付。

### 1.4 术语定义

| 术语 | 说明 |
|------|------|
| SKU | Stock Keeping Unit，最小库存单位 |
| 拼团 | 多人以折扣价购买同一商品的活动 |
| 锁单 | 拼团参团后冻结库存与订单的状态 |
| 成团 | 支付人数达到目标人数 |
| 券核销 | 支付成功后优惠券标记为已使用 |
| 正向/逆向交易 | 积分增加/减少的交易流水方向 |
| DCC | 动态配置中心（Zookeeper/Redis Pub-Sub） |
| ERP | 本系统中面向运营的后台管理端 |

## 2. 项目概述

### 2.1 项目定位

面向 C 端用户的完整电商营销平台，核心是"**可运营的营销引擎**"：以配置化活动（抽奖/拼团/积分/券）驱动用户增长与转化。

### 2.2 业务场景清单

| 场景 | 说明 |
|------|------|
| 用户登录与身份体系 | 微信扫码登录、JWT Token、用户画像 |
| 商品浏览与搜索 | 分类浏览 → ES 全文搜索 → 多维筛选 |
| 购物车 | 加购 → 合并 → 校验 → 一键下单 |
| 普通下单与支付 | 下单 → 统一收银台 → 微信/支付宝支付 → 发货 |
| 拼团购买 | 开团/参团 → 锁单 → 支付 → 成团/退款 |
| 营销抽奖 | 签到/购物得次数 → 概率抽奖 → 发奖 |
| 积分体系 | 行为返利积分 → 积分兑换抽奖次数/SKU |
| 优惠券体系 | 发券/领券 → 下单核销 → 退单退券 |
| 售后服务 | 申请退款/退货 → 审核 → 退款退券退积分 |
| 物流跟踪 | 发货 → 快递鸟查询 → 物流状态回写 |
| 首页运营 | Banner → 频道页 → 活动落地页 → 商品推荐 |
| 消息通知 | 微信模板消息 + 站内消息中心 + 拼团回调通知 |

### 2.3 技术目标（作为需求的约束）

- 架构：DDD 六边形架构，领域逻辑与技术框架解耦。
- 扩展性：营销玩法可插拔，新活动类型只需实现约定接口。
- 高可用：核心链路限流/熔断/降级，库存精确扣减，最终一致性保证。
- 可观测：Prometheus + Grafana 监控，ELK 日志，链路追踪。

## 3. 用户角色与用例

| 角色 | 说明 | 主要用例 |
|------|------|----------|
| 游客 | 未登录用户 | 浏览商品、搜索、加购（设备维度）、领券 |
| 注册用户 | 微信扫码登录用户 | 下单、支付、抽奖、拼团、积分、售后 |
| 运营人员 | 使用 ERP 后台 | 活动/策略/券/商品/订单/售后/首页配置、数据看板 |
| 系统管理员 | 平台维护 | 风控配置、监控告警、任务调度 |

核心用户故事（示例）：
- 作为用户，我可以用微信扫码 3 秒内完成登录，之后所有操作免登录。
- 作为用户，我可以搜索商品并按分类/价格/销量筛选排序。
- 作为用户，我可以把商品加入购物车，登录后自动合并设备购物车。
- 作为用户，我可以使用优惠券和积分抵扣下单，并选择微信或支付宝支付。
- 作为用户，我可以发起拼团邀请好友，成团后享受折扣价。
- 作为用户，我可以签到、抽奖、用积分兑换奖品。
- 作为运营，我可以创建/审核/上下线营销活动并实时查看数据。

## 4. 功能需求

> 编号规则：FR-<模块>-<序号>。优先级：P0 核心必须 / P1 重要 / P2 增强。

### 4.1 用户模块（FR-USER）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-USER-01 | 微信扫码登录 | 获取二维码 ticket → 用户扫码 → 前端轮询检测 → 返回 JWT Token | P0 |
| FR-USER-02 | 登录状态鉴权 | 所有业务接口携带 Token，拦截器校验，未登录返回 401 | P0 |
| FR-USER-03 | 用户信息 | 查询当前用户信息（昵称/头像/手机号） | P0 |
| FR-USER-04 | 收货地址管理 | 新增/修改/删除/查询收货地址列表 | P0 |
| FR-USER-05 | 用户状态 | 用户状态：正常/冻结/注销；冻结用户禁止下单 | P1 |
| FR-USER-06 | 登录轮询限流 | 同一 ticket 每 2 秒允许 1 次轮询；ticket 有效期 5 分钟 | P1 |

**验收标准**：用户扫码后 ≤ 5 秒内完成登录；同一 ticket 5 分钟内有效；冻结用户请求业务接口被拒绝。

### 4.2 商品模块（FR-PRODUCT）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-PRODUCT-01 | 商品列表 | 分页查询，支持分类筛选 | P0 |
| FR-PRODUCT-02 | 商品详情 | 商品信息 + SKU 列表 + 库存 + 价格 | P0 |
| FR-PRODUCT-03 | 分类管理 | 商品分类树 | P1 |
| FR-PRODUCT-04 | 活动关联商品 | 查询活动关联商品列表 | P1 |
| FR-PRODUCT-05 | 商品/SKU 管理（ERP） | 商品、SKU 创建/编辑/上下架 | P1 |

**验收标准**：商品列表响应 < 200ms（命中缓存）；下架商品不出现在列表与搜索。

### 4.3 商品搜索模块（FR-SEARCH）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-SEARCH-01 | 全文搜索 | 关键词 + 分类 + 价格区间 + 排序（综合/销量/价格）分页 | P1 |
| FR-SEARCH-02 | 搜索建议 | 输入关键词自动补全 | P2 |
| FR-SEARCH-03 | 热门搜索词 | 返回热门搜索词列表 | P2 |
| FR-SEARCH-04 | 数据同步 | MySQL → ES 增量同步（Canal 或 SDK 直写） | P1 |

**验收标准**：搜索 P95 响应 < 500ms；商品数据变更后 ≤ 1 分钟在搜索结果生效。

### 4.4 购物车模块（FR-CART）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-CART-01 | 加入购物车 | 未登录按设备维度（`cart:device:{deviceId}`），登录后按用户维度 | P0 |
| FR-CART-02 | 购物车列表 | 实时校验库存/价格，标记失效商品（下架/售罄/价格变动） | P0 |
| FR-CART-03 | 数量更新/删除/选中 | 更新数量、移除、选中/取消选中、清空失效 | P0 |
| FR-CART-04 | 登录合并 | 登录后将设备购物车合并到用户购物车 | P1 |
| FR-CART-05 | 冷备份 | Redis 热数据（TTL 30 天）+ MySQL 冷备份 | P1 |

**验收标准**：加购后购物车总数即时可见；失效商品在购物车页有明确提示且不可下单。

### 4.5 订单模块（FR-ORDER）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-ORDER-01 | 订单预览 | 试算优惠：商品金额 − 优惠券 − 积分抵扣，校验库存价格变化 | P0 |
| FR-ORDER-02 | 创建订单 | 支持购物车批量下单、优惠券、积分抵扣；状态 CREATE | P0 |
| FR-ORDER-03 | 订单支付 | 发起支付获取收银台 URL，更新订单为 PAY_WAIT | P0 |
| FR-ORDER-04 | 订单查询 | 订单列表（按状态筛选）+ 订单详情（含物流） | P0 |
| FR-ORDER-05 | 取消订单 | 取消未支付订单，回滚券+积分+库存 | P0 |
| FR-ORDER-06 | 确认收货 | 用户确认收货或系统自动确认（签收后 N 天） | P0 |
| FR-ORDER-07 | 超时关单 | PAY_WAIT 超过 30 分钟自动 CLOSE，释放库存、退券退积分 | P0 |
| FR-ORDER-08 | 订单删除 | 逻辑删除 | P2 |
| FR-ORDER-09 | 订单状态机 | CREATE → PAY_WAIT → PAY_SUCCESS → DEAL_DONE / CLOSE / REFUND | P0 |

**验收标准**：下单事务内完成"锁券+冻积分+扣库存+建单"，任一失败整体回滚；超时关单任务每 5 分钟执行一次。

### 4.6 支付模块（FR-PAY）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-PAY-01 | 统一收银台 | 选择支付方式：微信/支付宝，返回支付 URL/表单 | P0 |
| FR-PAY-02 | 支付回调 | 支付宝/微信异步回调验签（RSA2），更新订单为 PAY_SUCCESS | P0 |
| FR-PAY-03 | 掉单补偿 | 定时查询支付单状态（每 1 分钟），补执行回调逻辑 | P0 |
| FR-PAY-04 | 支付单幂等 | 同一订单重复发起支付返回已有支付单 | P0 |
| FR-PAY-05 | 渠道抽象 | 支付渠道接口抽象，可扩展新渠道 | P1 |

**验收标准**：回调验签失败拒绝处理；重复回调幂等；掉单在 ≤ 2 分钟内自动补偿。

### 4.7 优惠券模块（FR-COUPON）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-COUPON-01 | 券模板管理 | 满减/折扣/运费/商品券模板 CRUD + 发布/停用 | P1 |
| FR-COUPON-02 | 领券 | 手动领取，校验限领数量/发行余量 | P1 |
| FR-COUPON-03 | 发券渠道 | 活动发放 / 签到赠送 / 新人自动发 | P2 |
| FR-COUPON-04 | 锁券 | 下单时券状态 UNUSED → LOCKED（与订单同事务） | P1 |
| FR-COUPON-05 | 核销 | 支付成功 LOCKED → USED | P1 |
| FR-COUPON-06 | 退券 | 订单取消/退款：USED/LOCKED → REFUNDED（可再次使用） | P1 |
| FR-COUPON-07 | 最优券计算 | 遍历可用券求最大优惠组合 | P1 |
| FR-COUPON-08 | 过期处理 | 定时扫描过期券标记 EXPIRED | P1 |

**验收标准**：锁券与订单创建同事务；退款后券可再次使用；过期券不可使用。

### 4.8 售后模块（FR-AFTERSALE）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-AFTERSALE-01 | 申请售后 | 仅退款 / 退货退款，填写原因、描述、凭证图 | P1 |
| FR-AFTERSALE-02 | 审核 | 商家审核通过/拒绝（备注原因） | P1 |
| FR-AFTERSALE-03 | 仅退款 | 审核通过 → 原路退款 + 退券 + 退积分 | P1 |
| FR-AFTERSALE-04 | 退货退款 | 审核通过 → 用户寄回 → 商家收货 → 退款+退券+退积分 | P1 |
| FR-AFTERSALE-05 | 售后状态机 | 待审核→审核通过→待寄回→寄回中→待收货→已完成 / 审核拒绝 / 已取消 | P1 |
| FR-AFTERSALE-06 | 事件时间线 | 记录申请/审核/寄回/收货/退款/完成事件 | P2 |

**验收标准**：仅退款审核通过后自动退款并退券退积分；退款与退券退积分通过本地消息表+MQ 保证最终一致。

| FR-LOTTERY-02 | 两种概率算法 | 单项概率（斐波那契散列 O(1)）+ 总体概率（动态重算分母） | P0 |

| FR-LOTTERY-07 | 量化抽奖 | 按人群标签量化抽奖 | P2 |
| FR-LOTTERY-08 | 数据预热 | 策略/活动装配（armory）缓存预热 | P1 |
| FR-LOTTERY-09 | 中奖记录/奖品列表 | 用户中奖记录、活动奖品列表查询 | P1 |

| FR-GROUPBUY-03 | 成团/失败 | 达目标人数成团；超时未成团自动退款 | P0 |

| FR-GROUPBUY-07 | 拼团首页/详情 | 优惠试算、进行中队伍、队伍成员与进度 | P1 |

**验收标准**：并发成团临界正确（无超团）；超时自动退单任务可靠；退单后队伍状态正确流转（含退单/已失败）。

### 4.14 积分模块（FR-CREDIT）

| 编号 | 需求 | 说明 | 优先级 |
|------|------|------|--------|
| FR-CREDIT-01 | 积分账户 | 累计/可用/冻结三余额，防透支（原子 UPDATE + 余额校验） | P0 |
| FR-CREDIT-02 | 积分流水 | 正向/逆向交易流水（trade_type, out_biz_no 防重） | P0 |
| FR-CREDIT-03 | 行为返利 | 签到得积分、购物返积分（行为配置化） | P1 |

## 7. 数据需求

### 7.1 分库策略

- **公共配置库（uni_market / db00）**：商品、分类、SKU、营销活动、抽奖策略/奖品/规则树、折扣、行为返利配置、人群标签、优惠券模板、物流、首页 Banner/频道、拼团队伍、通知任务。
- **用户数据分库（uni_market_01 / uni_market_02）**：按 userId 哈希路由，每库 4 张分表（_000 ~ _003），共 8 分片：user、user_address、user_credit_account、user_credit_order、order、order_item、pay_order、lottery_order、user_award_record、group_buy_order、user_behavior_rebate_order、raffle_activity_account、cart_item、after_sale、user_coupon、user_message、mq_task。

### 7.2 数据一致性要求

- 订单创建事务：锁券 + 冻积分 + 扣库存 + 建单 同一事务。
- 积分调整原子 UPDATE 防透支（`available_amount + #{amount} >= 0`）。
- 拼团防重：biz_id（activityId_userId_count）唯一键。
- 积分交易防重：out_biz_no 唯一键。
- 通知/消息：本地消息表 + MQ + 定时补偿。

### 7.3 数据保留策略

- 购物车 Redis 热数据 TTL 30 天，MySQL 冷备份。
- 登录 ticket 缓存 5 分钟。
- 历史订单/流水永久保留，支持分页查询。
