## 1. 总体原则

| 原则 | 说明 |
|------|------|
| 黄金指标先行 | 先监控 RED（请求率/错误率/延迟）与 USE（利用率/饱和度/错误） |
| 可观测优先 | 指标 + 日志 + 链路三位一体（Prometheus + ELK + traceId） |
| 告警宁精勿滥 | 每条告警可行动、有阈值依据；避免噪音告警疲劳 |
| 覆盖核心链路 | 下单/支付/抽奖/拼团/库存/MQ/任务 必须监控 |
| 告警可响应 | 每条告警有分级、处理人、时限 |

## 2. 监控指标模型

### 2.1 RED（请求维）

| 指标 | 说明 | 示例 |
|------|------|------|
| Rate | 请求速率 | QPS（按接口/模块） |
| Errors | 错误率 | 5xx 占比、业务错误码分布 |
| Duration | 延迟 | P50/P95/P99 RT |

### 2.2 USE（资源维）

| 指标 | 说明 |
|------|------|
| Utilization | 利用率：CPU、内存、连接池、磁盘 |
| Saturation | 饱和度：线程池排队、MQ 积压、GC 停顿 |
| Errors | 错误：Full GC、OOM、连接失败 |

### 2.3 业务指标

库存水位、订单量、支付成功率、抽奖次数、拼团成团率、券核销率、任务执行成功率等（见 §4）。

## 3. 指标命名规范

统一 Prometheus 命名：`<命名空间>_<子系统>_<指标>_<单位>`

```
unimarket_order_created_total          # 订单创建总数（Counter）
unimarket_pay_success_rate             # 支付成功率（Gauge）
unimarket_raffle_draw_seconds         # 抽奖耗时（Histogram）
unimarket_stock_activity_available     # 活动库存剩余（Gauge）
unimarket_mq_queue_depth               # MQ 队列积压（Gauge）
unimarket_job_execute_success_total    # 任务执行成功数（Counter）
```

| 后缀 | 含义 |
|------|------|
| `_total` | Counter 计数 |
| `_seconds` | Histogram 耗时 |
| `_available` / `_depth` | Gauge 水位 |
| `_success_rate` | Gauge 比例 |

**标签约定**：接口级指标带 `method`、`path`、`status`；业务指标带 `activity_id`、`order_type` 等，标签基数可控（禁高基数如 userId）。

## 5. 告警规则设计

### 5.1 规则书写要点

```yaml
# prometheus/rules.yml 示例
groups:
  - name: unimarket-core
    rules:
      - alert: 支付成功率下降
        expr: unimarket_order_pay_success_rate < 0.95
        for: 5m                    # 持续 5 分钟才触发（防抖动）
        labels:
          severity: P1
        annotations:
          summary: "支付成功率低于 95%"

      - alert: 回调验签失败激增
        expr: rate(unimarket_pay_notify_verify_fail_total[5m]) > 0.5
        for: 5m
        labels:
          severity: P1

      - alert: MQ 积压过高
        expr: unimarket_mq_queue_depth > 10000
        for: 5m
        labels:
          severity: P1

      - alert: 定时任务连续失败
        expr: rate(unimarket_job_execute_fail_total[10m]) > 0
        for: 10m
        labels:
          severity: P2
```

### 5.2 阈值设计原则

- 每个阈值标注依据（如"支付成功率 < 95% 持续 5 分钟"对应 SLA 目标）。
- `for` 持续时长防抖动；避免瞬时尖峰误报。
- 告警必须"可行动"：收到告警知道看什么、找谁、怎么处理。

## 6. 告警分级与响应

| 级别 | 定义 | 示例 | 响应时限 | 通道 |
|------|------|------|----------|------|
| P0 紧急 | 核心链路不可用/资金安全 | 支付全挂、验签连续失败、库存超发 | 立即（15min 内响应） | 电话/短信+IM |
| P1 严重 | 功能异常影响部分用户 | 支付成功率低、MQ 积压、任务失败 | 1h 内 | IM+邮件 |
| P2 一般 | 指标异常无用户感知 | 某接口延迟上升、库存将尽 | 当日 | IM |
| P3 提示 | 信息性告警 | 降级触发、拉黑增加 | 观察 | 面板/日报 |

**值班约定**（多人时）：P0/P1 告警值班人第一时间响应；单人项目至少保证 IM 通知可达。

## 7. Grafana 面板规划

| 面板 | 内容 |
|------|------|
| 总览 | QPS、错误率、P95 RT、CPU/内存（全局） |
| 接口 | 各接口 QPS/RT/错误率（按 method+path） |
| 订单支付 | 下单量、支付成功率、超时关单、掉单补偿 |
| 营销 | 抽奖次数/库存水位、拼团成团/失败 |
| 基础设施 | MySQL 连接/慢 SQL、Redis 命中率/内存、MQ 积压 |
| 任务 | XXL-Job 执行成功/失败/耗时 |
| 业务大盘 | GMV、订单量、活动转化、券核销率（ERP 看板数据源） |

**约定**：面板分组与 §4 指标清单对应；新指标上线同步建面板。

## 8. 检查清单

- [ ] 核心链路（订单/支付/抽奖/拼团/库存/MQ/任务）已有指标
