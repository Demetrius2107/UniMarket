> 适用于 UniMarket 统一商城前台的发布上线流程、变更审批、灰度与回滚约定。

## 1. 总体原则

| 原则 | 说明 |
|------|------|
| 小步快发 | 每次发布变更小、可独立验证，避免大版本堆积 |
| 可回滚优先 | 每次发布前确保上一版本可秒级回滚 |
| 先验证后放量 | 灰度验证通过再全量 |
| 发布留痕 | 每次发布有记录：版本、变更、验证、回滚预案 |
| 关键时段避险 | 促销/活动高峰期禁止发布（除非紧急修复） |

**发布 ≠ 部署**：部署是技术动作，发布是含验证、审批、放量的完整流程。

---

## 2. 发布类型与窗口

| 类型 | 说明 | 窗口 |
|------|------|------|
| 常规发布 | 功能/优化/非紧急修复 | 工作日低峰（如 14:00-17:00） |
| 紧急修复 | 线上故障修复 | 随时（需快速评估） |
| 活动发布 | 营销活动上线 | 避开用户高峰，活动前 1h 完成验证 |

**约定**：
- 常规发布避开周五下午与节假日（出问题无人响应）。
- 涉及支付/资金变更的发布，优先安排工作日并有完整验证方案。

---

## 3. 发布前准备

| 项 | 要求 |
|----|------|
| 代码 | 已合并 master，CI 全量流水线通过（见《CI/CD 规范》） |
| 测试 | 冒烟用例通过；涉及变更模块回归通过 |
| 配置 | Nacos 配置已准备好（新配置项），数据库 DDL 已执行或随发布执行 |
| 回滚预案 | 确认上一版本制品可用；数据变更有回滚方案（DDL 逆向/备份） |
| 通知 | 涉及第三方回调地址变更需提前通知（微信/支付宝/快递鸟） |
| 检查清单 | 按 §4 逐项确认 |

**数据库变更特别约定**：
- 先向后兼容的 DDL（加字段）再发布代码；删字段/改语义走独立步骤。
- 生产 DDL 执行前备份，执行窗口留足时间。
- 大表变更（加索引/改列）低峰执行，评估锁表影响。

## 4. 发布流程（Checklist）

```
□ 1. 确认发布内容与版本（制品 <version> + commit hash）
□ 2. 确认 CI 通过、冒烟用例通过
□ 3. 确认配置/密钥就绪（Nacos / 环境变量）
□ 4. 确认数据库变更脚本已执行/随发布执行，且可回滚
□ 5. 备份当前版本制品（回滚用）
□ 6. 执行部署（deploy.sh 或流水线），健康检查通过
□ 7. 冒烟验证核心链路（登录/下单/支付/营销）
□ 8. 观察监控 10-30 分钟（错误率/RT/业务指标）
□ 9. 灰度放量（如配置灰度，见 §5）
□ 10. 填写发布记录（§9 模板）
```

## 5. 灰度发布

| 场景 | 灰度方式 |
|------|----------|
| 全量小步 | 多实例部署：先 1 台（Nginx 权重 10%）→ 50% → 100% |
| 用户灰度 | 按 userId 哈希/百分比切流量（DCC 切量开关，见《配置规范》§5） |
| 功能开关 | 新功能走 DCC 开关，关闭时行为与旧版一致 |

**灰度规则**：
- 灰度比例 10% → 观察 15-30 分钟（错误率/业务指标）→ 50% → 全量。
- 灰度期发现异常 → 立即回滚灰度流量（权重调 0 / 开关关闭）。
- 涉及资金（支付/退款）的变更，灰度观察期适当延长。

## 6. 回滚策略

### 6.1 回滚触发条件

| 信号 | 动作 |
|------|------|
| 核心接口错误率飙升（>1%） | 立即回滚 |
| 业务指标异常（支付成功率骤降、库存超发） | 立即回滚 |
| 冒烟验证失败 | 回滚，不进入放量 |
| 用户投诉集中出现 | 评估后回滚 |

### 6.2 回滚方式

| 方式 | 适用 |
|------|------|
| 制品回滚 | 代码问题：恢复上一版本 jar，重启 |
| 配置回滚 | 配置问题：Nacos 回滚到上一版本（动态开关直接改回） |
| 数据回滚 | 数据问题：DDL 逆向脚本 / 备份恢复（需提前准备） |
| 流量回滚 | 灰度问题：权重调 0 / DCC 开关关闭 |

### 6.3 回滚操作要点

```bash
# 制品回滚（deploy.sh 支持）
./deploy.sh rollback          # 自动恢复上一版本制品并重启
curl http://localhost:8091/api/v1/health   # 健康检查
# 验证关键链路后恢复流量
```

- 回滚后 24h 内复盘：根因、规避措施、后续修复计划。
- 回滚动作要留痕（记录在发布记录"回滚"栏）。

## 7. 发布后验证

| 验证项 | 方法 |
|--------|------|
| 健康检查 | `/api/v1/health` 200 |
| 核心链路冒烟 | 登录/商品/下单/支付（沙箱）/抽奖 |
| 监控指标 | QPS/错误率/P95 无异常波动（对比基线） |
| 业务指标 | 订单量/支付成功率/营销指标正常 |
| 日志 | 无新 ERROR 刷屏，traceId 链路正常 |
| 任务 | XXL-Job 执行器在线，定时任务正常调度 |
| 第三方 | 支付回调/物流回调正常（如有变更） |

**观察期**：常规发布 30 分钟；涉及资金/营销变更 2 小时。

## 8. 事故响应流程

```
1. 发现（告警/用户反馈）→ 记录时间与现象
2. 评估分级（P0 核心链路/资金；P1 功能异常；P2 轻微）
3. 止损优先：P0/P1 立即回滚或关闭 DCC 开关，优先恢复服务
4. 定位：查日志（traceId）/指标/慢 SQL，确定根因
5. 修复：提 fix 分支 → CI 通过 → 紧急发布（或下个窗口）
6. 复盘：根因、影响范围、改进项（24h 内出记录）
```

**约定**：先止损再定位；禁止在未定位根因时反复重启（掩盖问题）。
