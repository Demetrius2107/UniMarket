## 1. 测试分层模型

采用**金字塔模型**：大量单元测试 + 适量接口测试 + 少量 E2E。

```
          ┌──────────┐
          │   E2E    │  少量（每阶段 3-8 条关键链路）
          ├──────────┤
          │  接口测试  │  中等（核心 API 全量）
          ├──────────┤
          │  单元测试  │  大量（Service/领域层核心分支）
          └──────────┘
```

| 层 | 工具 | 职责 | 执行时机 |
|----|------|------|----------|
| 单元测试 | JUnit 5 + Mockito | 领域服务/算法/规则引擎核心逻辑 | `mvn test`，每次提交 |
| 接口测试 | MockMvc / Postman 脚本 | Controller 入参校验、鉴权、响应结构 | 每模块完成 |
| E2E | 手工脚本 / 自动化（可选） | 端到端业务链路 | 每 Phase 验收 |

## 2. 测试命名规范

### 2.1 类名

```
<被测类>Test.java          # 单元测试
<被测类>ControllerTest.java # 接口测试（或 IntegrationTest 后缀）
```

- 与被测类同包，放 `src/test/java`。
- 禁止把所有测试堆在一个 `AllTests` 类里。

### 2.2 方法名（中文描述式）

```
方法名_场景_预期结果
```

| 写法 | 示例 |
|------|------|
| 推荐 | `doDraw_次数不足_抛出业务异常` |
| 推荐 | `createOrder_库存不足_回滚且不落单` |
| 推荐 | `calculateBestCoupon_多张券_返回最大优惠组合` |
| 避免 | `test1`、`testDraw`（无场景无预期） |

### 2.3 断言约定

- 必须断言**结果**而非只跑通（禁空断言）。
- 涉及金额用 `BigDecimal` 比较（`assertEquals(0, actual.compareTo(expected))`），禁止 float/double 直接相等。
- 异常测试用 `assertThrows`，并断言错误码。

```java
@Test
void doDraw_次数不足_抛出业务异常() {
    // given：用户活动账户次数为 0
    when(activityAccountRepository.query(...)).thenReturn(emptyAccount());
    // when / then
    BizException ex = assertThrows(BizException.class, () -> drawService.doDraw(...));
    assertEquals(ErrorCode.LOTTERY_COUNT_NOT_ENOUGH, ex.getErrorCode());
}
```

## 3. 单元测试规范

### 3.1 必须覆盖的核心逻辑（优先级）

| 模块 | 必测核心 |
|------|----------|
| 抽奖 | 单项概率散列边界、总体概率重算、排除已空奖品、决策树分支（锁次数/库存/兜底） |
| 拼团 | 成团临界（completeCount==target）、防重 bizId、三种退单策略、折扣四种策略计算 |
| 积分 | 防透支 UPDATE 校验、正向/逆向流水、兑换 7 步流程幂等 |
| 优惠券 | 最优券计算（贪心/组合）、锁券/核销/退券状态流转、过期判断 |
| 订单 | 状态机非法流转拒绝、金额计算顺序（商品-券-积分）、超时关单补偿 |
| 支付 | 验签失败拒绝、回调幂等（重复回调不重复处理） |
| 售后 | 状态机流转、仅退款/退货退款分支、退券退积分触发 |
| 风控 | 限流阈值、自动拉黑条件、降级开关生效 |

### 3.2 编写要求

- 纯逻辑（算法/计算/状态机）不依赖 Spring 上下文，直接 new + 单测。
- 依赖 Repository/MQ/外部 API 的 Service 用 Mockito mock，验证交互与结果。
- 每个测试独立（`@BeforeEach` 重置 mock），禁测试间共享可变状态。
- 定时任务方法按"可重跑幂等"设计后直接测其处理方法。

### 3.3 示例结构

```java
@ExtendWith(MockitoExtension.class)
class CouponCalculateServiceTest {

    @Mock private UserCouponRepository userCouponRepository;
    @InjectMocks private CouponCalculateService service;

    @Test
    void calculateBestCoupon_多张券_返回最大优惠() {
        // given：一张满 100 减 10、一张满 200 减 30
        Cart cart = buildCart(amountOf(300));
        // when
        CouponCombination best = service.calculateBestCoupon(cart, twoCoupons());
        // then
        assertEquals("T200", best.getCouponId());
        assertEquals(0, amountOf(30).compareTo(best.getDiscount()));
    }
}
```

## 4. 接口/集成测试规范

### 4.1 覆盖范围

每个 Controller 至少覆盖：

| 场景 | 断言 |
|------|------|
| 正常入参 | 200 + 响应结构正确 |
| 参数缺失/非法 | 400 + 错误 message |
| 未登录访问写接口 | 401 |
| 越权访问他人资源 | 403 |
| 触发业务错误码 | 对应业务 code（如库存不足 10001） |

### 4.2 写法

- 优先 Spring Boot Test + MockMvc（`@SpringBootTest` + `@AutoConfigureMockMvc`），鉴权用测试 Token。
- 或用 Postman Collection 维护接口用例（随接口评审清单更新），保证可回放。

```java
@SpringBootTest
@AutoConfigureMockMvc
class OrderControllerTest {

    @Autowired private MockMvc mockMvc;

    @Test
    void createOrder_未登录_返回401() throws Exception {
        mockMvc.perform(post("/api/v1/order/create")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{...}"))
            .andExpect(status().isUnauthorized());
    }
}
```

## 6. 测试数据与环境约定

- 独立测试库/环境：**禁止在开发库执行破坏性测试**；演示环境用沙箱支付。
- 测试数据统一前缀（如用户 `test_`、订单 `T-`）便于清理。
- 微信/支付宝用沙箱账号；快递鸟用测试 key；MQ/Redis 用独立实例（或内存替代）。
- 测试后清理：定时任务产生的数据、Redis key（统一 `test:` 前缀便于批量清）。

## 7. 覆盖率要求

| 层级 | 目标 |
|------|------|
| 领域核心（算法/状态机/计算） | 行覆盖 ≥ 90%，分支覆盖 ≥ 80% |
| Service 层 | 行覆盖 ≥ 70% |
| Controller / 基础设施 | ≥ 50%（以接口测试补充） |
| 全项目 | 行覆盖 ≥ 70%（Phase 10 统计验收） |

> 使用 JaCoCo 统计，`mvn test jacoco:report` 生成报告；未达标模块在评审时说明原因。

## 8. 测试准入/准出标准

### 准入（开始测试前）

- [ ] 功能代码编译通过，核心接口可用（Swagger 可调）
- [ ] 测试数据与环境就绪
- [ ] 相关 FR 需求已实现

### 准出（模块/Phase 交付前）

- [ ] 单元测试通过，核心逻辑分支全覆盖
- [ ] 接口测试通过（含鉴权/越权/参数校验）
- [ ] 对应 E2E 场景通过
- [ ] 覆盖率达标
- [ ] 缺陷清单关闭或明确遗留（有规避方案）
