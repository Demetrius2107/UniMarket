## 1. 压测目标与指标

### 1.1 目标（源自 SRS §5.1）

| 指标 | 目标值 |
|------|--------|
| 商品列表/详情（缓存命中） | P95 < 200ms |
| 全文搜索 | P95 < 500ms |
| 创建订单 | P95 < 500ms |
| 登录轮询命中 | < 200ms |
| 抽奖链路 | 1000 QPS 下库存不超发 |
| 拼团临界并发 | 成团/退款最终一致，无超团 |

### 1.2 关键性能指标（KPI）

| 指标 | 说明 |
|------|------|
| QPS/TPS | 吞吐量（每秒请求/事务数） |
| RT（P50/P95/P99） | 响应时间分位值 |
| 错误率 | 4xx/5xx/超时占比，目标 < 0.1% |
| 库存水位 | 压测后 Redis 与 DB 库存一致性校验 |
| 队列积压 | MQ 消费延迟（应 < 10s） |
| 资源利用率 | CPU / 内存 / GC / 连接数 |

## 2. 压测范围与场景

### 2.1 场景矩阵

| 场景 | 压测对象 | 目标并发 | 验证点 |
|------|----------|----------|--------|
| S1 全链路 | 登录→搜索→加购→下单→支付(模拟回调) | 500 并发 | 链路吞吐与 P95 |
| S2 抽奖并发 | `/raffle/draw` | 1000 QPS | 库存不超发、发奖必达 |
| S3 拼团临界 | `/groupbuy/lock_order` + 结算 | 500 并发 | 成团临界正确、防重 |
| S4 下单并发 | `/order/create`（含锁券/冻积分） | 300 并发 | 事务正确性、超时率 |
| S5 库存热点 | 同一 SKU 高并发抢购 | 1000 QPS | Redis+DB 扣减一致性 |
| S6 读热点 | 商品详情/首页/搜索 | 2000 QPS | 缓存命中率、P95 |

### 2.2 优先级

- **必做**：S1、S2、S5（Phase 12 验收核心，也是业务风险最高点）。
- **选做**：S3、S4、S6（视时间；S3 拼团临界建议必做，因最终一致性风险高）。

## 3. 工具与环境准备

### 3.1 工具选型

| 工具 | 用途 | 说明 |
|------|------|------|
| JMeter | 压测主工具 | 线程组 + 断言 + 汇总报告；脚本入库 `docs/jmeter/` |
| JMH | JVM 微基准 | 纯算法（抽奖概率/最优券计算）微基准 |
| Grafana + Prometheus | 压测监控 | 实时观察 QPS/RT/错误率/GC/连接 |
| 自研校验脚本 | 库存对账 | 压测后比对 Redis 与 DB 库存（或查 mq_task 补偿记录） |

### 3.2 环境要求

- **独立压测环境**：与开发/演示环境隔离，避免相互影响。
- 数据规模：模拟真实量级（商品 1 万、SKU 3 万、用户 10 万、活动库存充足且含部分售罄奖品）。
- 压测机与被测机分离；网络延迟按内网标准。
- 压测前记录基线（空负载时的 RT 与资源占用）。

## 4. 场景设计与压测数据

### 4.1 S2 抽奖并发（重点场景示例）

```
线程组：1000 并发持续 5 分钟（或按固定 QPS 1000 调控）
请求：POST /api/v1/raffle/draw
  body: { "activityId": "ACT_STRESS_01" }
数据准备：
  - 活动 ACT_STRESS_01：5 个奖品，含 1 个低概率大奖 + 1 个兜底奖品
  - 用户池：10 万 userId（保证分库分表路由分散，避免单分片热点）
  - 活动账户：每人 100 次
断言：HTTP 200 + code=200 或业务错误码（次数不足）
```

**并发安全校验**：
- 压测后：`strategy_award.award_surplus_count` 总数 = 初始 − 中奖数（按 award_id 汇总）。
- Redis `stock:activity:*` 与 DB 差值 ≤ 定时对账窗口内的正常误差，且 5 分钟内对账任务自动修正。
- mq_task 中 `state=2`（发送失败）比例 = 0，或补偿任务已全部重发成功。

### 4.2 S5 库存热点（重点场景示例）

```
线程组：1000 并发抢同一 SKU（库存 5000）
请求：POST /api/v1/order/create
断言：成功订单数 = 5000；其余返回库存不足(10001)；无 500 错误
```

**正确性校验**：
- 成功下单数 == 初始库存（不多不少）。
- 超时关单释放的库存被后续请求成功购买（可选验证）。

## 5. 压测执行流程

```
1. 准备：环境部署、数据灌入、监控面板就绪、基线记录
2. 冒烟：单线程跑通脚本（确认无脚本错误）
3. 阶梯加压：50 → 100 → 200 → 500 → 1000 QPS（每档 1-2 分钟）
4. 持续压测：目标 QPS 持续 5-10 分钟（观察稳定期）
5. 峰值验证：短暂提高 1.5 倍验证限流兜底（429 出现且无雪崩）
6. 压后校验：库存对账、mq 补偿、数据一致性脚本
7. 记录：按第 6 节模板输出结果报告
```

**注意**：
- 每档加压观察错误率与 RT，出现拐点（错误率上升/RT 陡增）时记录并降档确认瓶颈点。
- 压测期间同时观察：GC 频率与停顿、DB 连接池、Redis 内存、MQ 积压。
- 抽奖/拼团压测后必须做**数据校验步骤**（一致性），不能只看吞吐。

## 7. 瓶颈定位与调优

| 症状 | 排查方向 | 常见调优 |
|------|----------|----------|
| RT 高 | 慢 SQL、N+1 查询、锁等待 | 加索引、批量查询、缓存预热 |
| 错误率上升 | 连接池打满、Redis 超时 | 调池大小、降级/限流、缩短锁内逻辑 |
| 库存不一致 | 扣减逻辑缺陷、补偿任务失效 | 核对三层库存方案（SDS §10.3） |
| GC 频繁 | 对象分配过多、缓存膨胀 | 调堆参数、检查缓存 TTL 与大小 |
| 热点 key | 单分片/单 key 竞争 | 分段锁、分片 key、本地缓存 |
| 队列积压 | 消费慢、生产突增 | 增加消费者、批量消费、限流保护 |

**调优原则**：一次只改一个变量，改后重新压测对比；调优以"达到目标"为准，不做无依据的过度优化。

## 8. 压测准入/准出

### 准入

- [ ] 功能测试通过，核心链路无阻塞缺陷
- [ ] 压测环境与数据就绪，监控面板可用
- [ ] 已记录环境基线

### 准出（Phase 12 验收）

- [ ] S1/S2/S5 达标（QPS/RT/错误率）
- [ ] 库存一致性校验通过（抽奖与热点场景）
- [ ] 拼团临界（S3）无超团、退款一致
- [ ] 限流兜底生效（峰值 429 无雪崩）
- [ ] 压测报告输出，遗留问题有对策
